### S1（W1-U1/U2）手写有界阻塞队列

**为什么先学这个**  
队列是所有生产者-消费者流水线的骨架。写不对它，后面三线程流水线一定出问题（丢数据、死锁、CPU 烧满）。

**要读的原项目代码**

| 位置                                | 看什么                                   |
| --------------------------------- | ------------------------------------- |
| `Tools/CircularQueue.h` 全文（214 行） | 正统实现：双条件变量 + 谓词 wait + move 语义        |
| 同文件 `push()` 83-91 行              | 满队列时 `not_full_.wait(lock, 谓词)` 的标准写法 |
| 同文件 `pop_wait()` 145-172 行        | 超时版 `wait_for` 和无限等待版的区别              |
| 同文件 `shutdown()` 207-211 行        | 关闭时为什么要 `notify_all` 两个条件变量           |

**要写的代码**  
`00_thread_lab/include/CircularQueue.h` —— 只保留 public 接口，实现全部重写。

关键要求：

1. 用 `std::condition_variable`，**不允许出现 `sleep_for` / `yield` 在等待逻辑里**
2. `push` 在 `overwrite=true` 时挤掉最老的并累加 `dropped`；`false` 时阻塞并累加 `blocked`
3. `pop_wait` 必须响应 `shutdown()`
4. 维护 `pushed/popped/dropped/blocked` 四个计数（测试靠它判定）
5. 移动语义要真的生效（`cv::Mat` 6MB，深拷贝代价很大）

**当前 v0 基线（我已跑过，记下来当对照）**

```
[PASS] T1 单生产者-单消费者   墙钟    35.2ms | CPU     12.6 Mcyc
[FAIL] T2 4生产者-4消费者      墙钟  2027.1ms | CPU    138.7 Mcyc  (线程未被唤醒)
[PASS] T3 覆盖模式(实时优先)  墙钟  1558.8ms | CPU     35.5 Mcyc
[PASS] T4 阻塞模式(不丢数据)  墙钟  7105.9ms | CPU    121.6 Mcyc

```
5 PASS，且 T2 从 2027ms → < 20ms，T4 从 7106ms → < 60ms

### S2（W1-U3）三线程流水线

**目标**：把「队列」变成「流水线」，体会「中段慢会怎样」。

**任务**  
新建 `00_thread_lab/src/pipeline.cpp`，实现：

```
Thread-A 读取  每秒产 100 条数据（模拟相机 100fps）
   ↓ CircularQueue<string>(20, 覆盖)
Thread-B 处理  每条耗时 15ms（模拟推理）
   ↓ CircularQueue<string>(100, 覆盖)
Thread-C 输出  每秒写 50 条（模拟落库）
```

跑 10 秒，统计：

- A 产了多少、B 处理了多少、C 输出多少
- 每个队列的 `dropped` 数
- 三个线程各自的 CPU 占用

**然后做一个实验**：把 B 的耗时从 15ms 改成 5ms，再跑一次。观察 `dropped` 怎么变。

**这个实验的意义**  
它就是原项目的行为：相机 30fps 一直出图，推理如果跟不上，`frameQueue` 就会一直覆盖丢帧。理解这点，你就明白为什么界面上「有时候跳帧」。

### S3（W2-U1）改造原项目：消灭忙轮询

**这一步是整个计划里最有成就感的环节。**

**问题定位**

```cpp
// Server/ImageProcessing.cpp:176  ImageSegWorker
while (State::ThreadRun)
{
    auto newImg = State::frameQueue.pop();       // 非阻塞，空了立刻返回 nullopt
    if (!newImg.has_value() || newImg->empty())
        continue;                                 // ← 立刻回到 while，再 pop，再 continue
    ...
}
```

没有图的时候，这个循环就是一个**把 CPU 跑满的空转**。三个线程都是这样写的。

实测：无相机、无图的情况下，**6 秒消耗 11.13 秒 CPU ≈ 185% 单核**。

**任务**

1. 先实测基线：启动 `release\ImageSeg.exe`，用任务管理器看 CPU 占用，记下来
2. 把三处 `pop()` 改成 `pop_wait(std::chrono::milliseconds(100))`
3. 重新编译，再测 CPU

**注意 `pop_wait` 的返回值语义**  
返回 `nullopt` 有两种可能：队列空（超时）或已关闭。改造后不能简单 `continue`，要判断 `State::ThreadRun`。

**验收**

- CPU 从 185% 降到 < 10%
- 程序功能不变（能正常跑本地图片回放）

**自检题**

1. 为什么 `pop_wait(100ms)` 的超时值不能设成 0（无限等待）？（提示：`ThreadRun` 变成 false 之后线程怎么退出）
2. 改成阻塞等待后，相机停止出图，线程会卡在哪里？会不会影响退出？这正是 S4 要解决的。

### S4（W2-U2）优雅停止

**问题定位**

```cpp
// Server/ImageProcessing.cpp:131  Start()
imageSegThread = std::thread(&ImageProcessing::ImageSegWorker, this);
SetThreadPriority(..., THREAD_PRIORITY_HIGHEST);
imageSegThread.detach();     // ← detach 之后彻底失控
```

三个线程全部 `detach`，`Server::Start()` 里那个定时器线程也一样：

```cpp
std::thread timerRun(&Server::Timer_1s, this);
timerRun.detach();           // 局部对象 + detach，this 的生命周期无人保证
```

后果：程序退出时线程可能还在访问已析构的静态对象，偶发崩溃，且**永远无法优雅关闭**。

**任务**

1. 保留 `std::thread` 成员，不要 detach
2. 加 `Stop()`：置 `ThreadRun = false` → 对三个队列调 `shutdown()` → `join()` 所有线程
3. 在 `Widget` 析构或 `aboutToQuit` 时调用 `Stop()`
4. 验证：点关闭按钮，进程在 1 秒内完全退出，任务管理器里没有残留

**验收**

- 连续启动/关闭 10 次，无一次残留进程、无一次崩溃
- 关闭耗时 < 1 秒

**参考**

- `Server/Server.cpp:125-141` `Start()`
- `Server/Server.cpp:265` `Timer_1s()` —— 注意它里面是 `while(ThreadRun) { sleep(1s); ... }`，关闭最坏要等 1 秒

**自检题**

1. `std::thread` 析构时如果还是 joinable，会发生什么？
2. 为什么 `detach()` 之后不能 join？detach 的线程还能被停止吗？
3. 定时器线程用 `sleep_for(1s)` 轮询，怎么让它「立刻响应关闭」而不是等满 1 秒？（提示：条件变量的 `wait_for` 也能当可中断 sleep 用）

## 七 卡住了怎么办

**优先级顺序**（先自己试，再问）：

1. **看测试输出的具体数字**。`T4 消费 55921/100000` 这种，说明没死锁，只是慢。
2. **二分定位**：把队列容量改成 1，逻辑问题会立刻暴露（每次 push 都必须等 pop）。
3. **加打印**：在 `push` / `pop` 前后打计数，跑 100 条看序列是否正确。
4. **Deadlock 排查**：Windows 上用 VS 的「调试 → 全部中断」，看各线程的调用栈卡在哪。
5. 再来问我，**带上具体数字和你的实现代码**。

**不建议**：
- 直接搜「C++ 线程安全队列」抄一份。你抄完测试能过，但 S3/S4 改原项目时依然不会——因为那边的问题不是「队列写错」，是「用法错」。
