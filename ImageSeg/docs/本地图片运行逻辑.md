# 本地图片回放：从磁盘到结果的完整运行逻辑

> 这份文档只讲**一条路径**：不用相机，直接喂本地图片，看它怎么被处理。
> 相机在线路径只在必要的地方做对照。
> 所有行号对应当前工作区代码（`ImageSeg/` 下），改动代码后行号会漂移，按函数名找即可。

---

## 0. 一句话总览

```
磁盘上的图  →  cv::Mat  →  frameQueue  →  分割线程  →  分类线程  →（吹气线程，本地模式跳过）→  showImgQueue  →  界面
              ^                          ^            ^                                          ^
         Server::DownImage          ImageSegWorker  ImageClsWorker                        Widget 50ms 定时器
```

一张图 = 一帧**完整大图**，在本地模式下不做相机那种纵向拼接。
整条链路上有 **3 个工作线程 + 2 个 Qt 定时器 + 3 个线程安全队列**。

### 2.2 `Widget::Widget()`（Widget.cpp:19-89）

构造过程按顺序做了 6 件事：

```cpp
ui->setupUi(this);                    // ① 建界面
setWindowFlags(...);                  // ② 无边框 + 拖拽
ui->Tab2_UpImg_Btn->setEnabled(false); // ③ 本地图片按钮先禁用

    Server::GetPtr()->Start();
}).spawn();
// ... TableForm / SettingForm 挂到 tab 上
timer_Tab1->start(1000);              // ⑥ 启动 1s 产量刷新定时器
```

**为什么初始化要丢到后台线程？**
因为 `Server::Start()` 里要加载两个 ONNX 模型并 warm up，CPU 上要几百毫秒到几秒。放主线程会把界面卡住。

**这里有个坑**：`QtConcurrent::task` 是 Qt 6.7+ 的 API，工程在原开发机（Qt 6.11）上没问题。本机 Qt 6.5.3 上 `QtConcurrent::task` 存在但头文件路径不同 —— 这也是为什么原来 `#include <QtConcurrentTask>` 编译不过。

初始化完成后 `QFutureWatcher::finished` 会把 `State::imgProcessInitSuccess` 置 true（这个标志目前没有其他代码在用，属于预留）。

### 2.4 `Server::Init()` —— 读配置（Server.cpp:33-96）

这是"配置从哪来"的答案，**从头到尾只有一个数据源：SQLite 库**。

```cpp
void Server::Init()
{
    // 第一件事：定模型目录（必须在这里，不能在静态初始化里）
    State::ModelInfo::SegModelPath = (QCoreApplication::applicationDirPath() + "/mode/seg").toStdString();
    State::ModelInfo::ClsModelPath = (QCoreApplication::applicationDirPath() + "/mode/cls").toStdString();

    auto sql = m_databasePool.getConnectionAutoPtr();
    QSqlQuery query(*sql);
    if (query.exec("select * from ConfigInfo;")) {
        QVariantMap configInfo;
        while (query.next())
            configInfo[query.value("Key").toString()] = query.value("Value");
        // ↓ 之后逐项搬到 State 里
    }
}
```

**两个注意点（都是踩过的坑）**：

1. **模型路径不能写在静态初始化里**。原代码是
   `std::string State::ModelInfo::SegModelPath = (QCoreApplication::applicationDirPath() + "/mode/seg").toStdString();`
   全局对象构造时 `QApplication` 还没创建，`applicationDirPath()` 返回**空串**，路径就变成了 `"/mode/seg"`。必须挪到 `Init()` 里。

2. **`QVariant("0").toBool()` 是 `true`**。`ConfigInfo.Value` 是 TEXT 类型，读到的是字符串 `"0"`/`"1"`。`toBool()` 的规则是"非空字符串即 true"，所以 `"0"` 会被判成 true。必须 `toInt() != 0`：
   ```cpp
   State::ModelInfo::UseGPU = (configInfo["UseGPU"].toInt() != 0);
   ```

### 2.5 `Server::Start()` —— 顺序很重要（Server.cpp:125-139）

```cpp
void Server::Start()
{
    m_camera.OpenRGBCamera();       // ① 开相机（没相机就打印 Find No Devices，不影响后续）
    m_imgProcess.LoadModel(...);    // ② 加载模型（最耗时，最可能失败）
    PlcClient::GetPlcPtr()->Open(); // ③ 连 PLC
    ModbusTcpSlave::GetPtr()->Open(State::ModbusInfo::Port);  // ④ 起 Modbus 从站
    State::ThreadRun = true;        // ⑤ 放行所有 worker 的 while 循环
    m_imgProcess.Start();           // ⑥ 真正创建 3 个线程
    std::thread timerRun(&Server::Timer_1s, this);  // ⑦ 1 秒一次的产量落库线程
    timerRun.detach();
}
```

**顺序为什么关键**：
- `ThreadRun = true` 必须在 `Start()` 之前。反过来的话线程一起来就看到 `ThreadRun == false`，直接退出。
- `LoadModel()` 必须在 `Start()` 之前。worker 一跑起来就要用 `m_seg`，空指针会崩。

### 2.6 `ImageProcessing::LoadModel()` —— 模型怎么加载（ImageProcessing.cpp:28-127）

分四步：

**第一步：查 `ModeInfo`，拿到模型文件名**

```cpp
QString modeSql = QString("select * from ModeInfo where MainId = %1;").arg(State::ModelInfo::Mode);
// → SegModel = "hei_huizong_250428.onnx", ClsModels = "hezhuang5.onnx", Channel = 1
```

**第二步：查 `ModeDetail`，拿到品类 → 吹气表**

```cpp
SELECT * FROM ModeDetail WHERE MainId = 1;
// → 28 条：baituo / biao / can / can-1 / cibai / dabai / guan / ... 每条含 TypeName、TypeBlow、SortId
info.ClsTypes[detail.ClsModel].append(detail);   // 按分类模型名分组
```

> 🔴 **这里有个隐性强约束**：分类模型输出的第 i 个值，对应 `classes[i]`，而 `classes` 就是按 `ModeDetail.SubId` 顺序取的 `TypeName`。
> **数据库里 28 个品类的顺序，必须和模型训练时的类别顺序完全一致**，否则分类结果会张冠李戴且不报错。
> 换分类模型时，`ModeDetail` 必须跟着重排。

**第三步：加载分割模型**

```cpp
std::string segPath = State::ModelInfo::SegModelPath + "/" + segName;  // <exe>/mode/seg/xxx.onnx
m_seg = std::make_unique<Yolov8SegOnnx>();
m_seg->ReadModel(segPath, State::ModelInfo::UseGPU);
```

`ReadModel` 内部（Yolov8SegOnnx.cpp:9-171）：

1. `CheckModelPath()` — 用 `_access()` 检查文件在不在，不在直接返回 false
2. 查 `GetAvailableProviders()` 里有没有 `CUDAExecutionProvider`
3. 有且 `isCuda` → `OrtSessionOptionsAppendExecutionProvider_CUDA()`
   **注意：这一步只是"声明要用 CUDA"，真正加载 `cublas64_12.dll`/`cudnn` 是在创建 Session 时**
4. `new Ort::Session(env, modelPath, options)` ← **这里才会真正加载 CUDA 运行库**
5. 读输入/输出节点名、shape
6. `warmUp=true` 时跑 10 次空推理（Yolov8SegOnnx.cpp:145-165）

> 💥 **本机实测**：`UseGPU=1` 时日志打到 `Infer model on GPU!` → `Start warming up` 进程就退出了。
> 原因就是第 4 步加载不到 `cublas64_12.dll`（本机只有 CUDA 11.8），异常被 catch 后状态已经损坏。
> 所以本机必须 `UseGPU=0`。

**第四步：加载分类模型**

```cpp
for (int i = 0; i < clsNames.size(); i++) {
    auto cls = std::make_unique<Yolov8ClsOnnx>();
    DL_INIT_PARAM param;
    param.modelPath = State::ModelInfo::ClsModelPath + "/" + clsNames[i];
    param.cudaEnable = State::ModelInfo::UseGPU;
    cls->CreateSession(param);        // 不做 warm up（分类模型小，无所谓）
    cls->classes = clsTypeVec[i];     // ← 品类名，顺序 = ModeDetail 顺序
    m_clsList.push_back(std::move(cls));
}
```

`DL_INIT_PARAM` 的默认值（Yolov8ClsOnnx.h:33-44）：`imgSize = {224,224}`、`rectConfidenceThreshold=0.3`、`intraOpNumThreads=1`。

> ⚠ `CreateSession` 开头有个中文路径检查（Yolov8ClsOnnx.cpp:117-124）：
> `std::regex_search(modelPath, "[\u4e00-\u9fa5]")` —— **模型路径带中文会直接 return，模型加载失败且只有一行 cout**。
> 这就是为什么模型必须放 `release\mode\` 这种纯英文路径下。

**第五步：设置通道分界线**

```cpp
if (State::ModelInfo::Channel > 1)
    m_channelBoundary = info.ChannelBoundary;   // 多通道才用
// 单通道时保持构造函数里的 2048
```

### 2.7 `ImageProcessing::Start()` —— 三个线程（ImageProcessing.cpp:131-147）

```cpp
imageSegThread = std::thread(&ImageProcessing::ImageSegWorker, this);   // 分割
imageClsThread = std::thread(&ImageProcessing::ImageClsWorker, this);   // 分类
setRangeThread = std::thread(&ImageProcessing::ImageRangeWorker, this); // 吹气
imageSegThread.detach();  // 三个都 detach
```

`SetThreadPriority()` 把分割/分类线程提到 `THREAD_PRIORITY_HIGHEST`，吹气线程 `ABOVE_NORMAL`。
（`detach` + 析构里 `joinable()` 判断的组合其实是矛盾的：detach 之后 `joinable()` 永远 false，析构时不会等待。学习时注意这个细节。）

> 已用 `#if QT_VERSION >= QT_VERSION_CHECK(6,7,0)` 两个版本各写一个槽修掉。

### 3.2 选目录 → 扫文件（Server.cpp:142-161）

```cpp
void Server::SetReadImagePath(std::string path)
{
    readImgPath = path;
    m_imgList.clear();
    readIndex = 0;                        // ← 换目录一定重置游标

    QDir dir(QString::fromStdString(path));
    QStringList filters;
    filters << "*.jpg" << "*.jpeg" << "*.png" << "*.bmp" << "*.tif" << "*.tiff";
    const QFileInfoList files = dir.entryInfoList(filters, QDir::Files, QDir::Name);
    for (const QFileInfo& fi : files)
        m_imgList.push_back(fi.absoluteFilePath().toStdString());
}
```

**为什么不用 `cv::glob`**（原实现）：
- `cv::glob(path + "/*.jpg")` 只认 `.jpg`，现场存的 bmp/tif 一张都扫不到
- `cv::glob` 底层是 `_findfirst` 窄字符 API，**中文路径枚举结果为空**
- 同理 `cv::imread` 也是窄字符，中文路径返回空 Mat

所以改成 `QDir` 枚举 + `QFile` 读字节 + `cv::imdecode`。

**`QDir::Name` 排序是字符串序**：`img_1.jpg, img_10.jpg, img_2.jpg`。如果文件名没有补零，播放顺序会和你预期不同。

### 3.4 「下一张」到底做了什么（Server.cpp:220-241）

```cpp
void Server::DownImage()
{
    if (m_imgList.empty()) { qDebug() << "本地图片列表为空"; return; }
    if (readIndex >= (int)m_imgList.size()) { qDebug() << "已经是最后一张"; return; }

    cv::Mat img = ReadLocalImage(m_imgList.at(readIndex));   // ① 解码
    if (!img.empty())
        State::frameQueue.push(img);                          // ② 丢进全局帧队列
    readIndex++;                                              // ③ 游标后移
}
```

`ReadLocalImage`（Server.cpp:164-186）：

```cpp
QFile file(QString::fromStdString(path));
if (!file.open(QIODevice::ReadOnly)) { ... return img; }
const QByteArray data = file.readAll();
std::vector<uchar> buf(data.begin(), data.end());
img = cv::imdecode(buf, cv::IMREAD_COLOR);   // ← IMREAD_COLOR 统一成 3 通道 BGR
```

**关键点**：
- `frameQueue` 是 `CircularQueue<cv::Mat>`，容量 **20**，**覆盖模式**（满了丢最老的）
- push 之后就**不再管了**，后续全靠 worker 自己 pop
- `readIndex` 语义是「下一张要播的位置」，当前显示的是 `readIndex - 1`

**「上一张」**（Server.cpp:198-217）实现要绕一点，因为游标语义：

```cpp
const int cur = readIndex - 1;          // 当前正在显示的
const int target = cur > 0 ? cur - 1 : 0;
// ... 读 target 那张，push
readIndex = target + 1;
```

> 原实现是 `readIndex = readIndex > 0 ? readIndex - 1 : 0;` 然后 `at(readIndex - 1)`。
> 当 `readIndex == 0`（还没播过任何一张）时，`readIndex - 1` 在 `vector::at()` 里是 `size_t` 下溢 → `at(18446744073709551615)` → 抛 `out_of_range` → 未捕获 → **进程直接退出**。已修。

### 3.5 时序：点一下按钮，数据走到哪

```
[UI 线程]  点击"下一张"
    │
    ├─ Widget::on_Tab2_DownImg_Btn_clicked()
    │      └─ Server::DownImage()
    │            ├─ ReadLocalImage()      QFile 读字节 → imdecode → cv::Mat
    │            └─ frameQueue.push(mat)  ← 队列容量 20，满了覆盖最老
    │
    └─ 返回，界面无变化（用户会以为"没反应"）

[分割线程]  ImageSegWorker 正在 while 循环里 pop()
    │            └─ 拿到这张 Mat，开始推理
    ▼
[分类线程]  ...
    ▼
[UI 线程]  50ms 定时器 → showImgQueue.pop() → 更新图像控件
```

**所以点完「下一张」到界面出结果有延迟**，延迟 = 分割推理 + 分类推理（CPU 上通常 0.3~1 秒/张）。

### 4.2 相机模式 vs 本地模式：拼图逻辑的差别

**相机模式**（`IsReadImg == false`）：
相机每帧是 `2048×512`（宽×高）。`oldImg` 初始是 `Mat(512, 2048, CV_8UC3, 0)`（全黑），每次：

```
第 1 帧：vconcat(全黑512, frame1_512)  → 1024×2048   ← 上半是黑的
第 2 帧：vconcat(frame1_512, frame2_512) → 1024×2048  ← 正常的"两帧拼一张"
第 3 帧：vconcat(frame2, frame3) → 1024×2048
...
```

**一张大图恒定为 2048×1024**。这是整个项目的隐含前提，后面很多常量都基于它：
- `GetMask2` 里坐标钳制到 `2048` / `1024`（Yolov8_Utils.cpp:230-231）
- 分类阶段的 Y 范围过滤按 1024 高设计（`BlowAreaStart=450`、`BlowAreaEnd=1020`）
- 吹气位置换算 `range->first * 512 * HightProportion`

> 为什么要拼两帧？因为相机是**线扫/低分辨率高速采集**，单个物体跨两帧，必须拼起来才完整。

**本地模式**（`IsReadImg == true`）：直接 `clone()` 当整图，**不拼接**。

> 🔴 **所以本地图片的正确尺寸是 2048×1024**（或更小）。
> 如果你放一张 2048×1536 的图，超过 y=1024 的部分在 `GetMask2` 里会被**硬钳制**：
> ```cpp
> if (vertices[i].x > 2048) vertices[i].x = 2048;
> if (vertices[i].y > 1024) vertices[i].y = 1024;
> ```
> 结果就是下部物体的 `bigBox` 塌成一条线，裁剪出来的小图是错的，分类必然失败。

### 4.3 预处理：LetterBox（Yolov8_Utils.cpp:24-84）

模型输入固定 `640×640`，进来之前要做**等比缩放 + 灰边填充**：

```cpp
float r = min(640.0/h, 640.0/w);        // 取小的那个比例，保证整图塞得下
if (!scaleUp) r = min(r, 1.0f);         // ← 关键：只缩不放

new_w = round(w * r);  new_h = round(h * r);
dw = (640 - new_w) / 2;  dh = (640 - new_h) / 2;

resize(image, out, Size(new_w, new_h));
copyMakeBorder(out, out, top, bottom, left, right, BORDER_CONSTANT, Scalar(114,114,114));
params = { r, r, left, top };            // ← 反算坐标要用
```

以 **2048×1024** 为例：

```
r = min(640/1024, 640/2048) = min(0.625, 0.3125) = 0.3125
new_w = 2048 * 0.3125 = 640
new_h = 1024 * 0.3125 = 320
dw = 0, dh = (640-320)/2 = 160
→ 缩放后 640×320，上下各补 160 灰边 → 640×640
params = { 0.3125, 0.3125, 0, 160 }
```

**这张"缩放比 0.3125"就是精度天花板**：原图上 10 像素的东西，进模型只剩 3 像素。

再算一下别的尺寸：

| 原图尺寸 | 缩放比 r | 模型里物体实际宽度（原图 100px 物体） |
|---|---|---|
| 2048×1024 | 0.3125 | 31 px ✅ 可用 |
| 2048×512 | 0.3125 | 31 px ✅ |
| 4096×1024 | 0.156 | 16 px ⚠ 勉强 |
| 8192×1024 | 0.078 | 8 px ❌ 基本检不出 |
| 2048×1536 | 0.3125（宽度限制） | 31 px，但高度只到 1024 有效 |

> `if (!scaleUp) r = min(r, 1.0f)` 意味着**小图不会被放大**。一张 512×256 的图会保持原样再补灰边，模型里只有中间一小块有内容。

### 4.5 后处理：三个步骤（Yolov8SegOnnx.cpp:236-313）

**① 解码 YOLOv8 的输出格式**

YOLOv8-seg 的 output0 形状是 `[1, 4+nc+32, 8400]`，导出时是"通道在前"，所以要转置：

```cpp

//  116 = 4 (cx,cy,w,h) + 1 (类别分数，本项目只有 bottle 一个类) + 32 (mask 系数)
```

对每一行（8400 个候选框）：

```cpp

}
```

**② NMS 去重**


**③ 生成 mask（最耗时的一步）**

```cpp

```

`GetMask2`（Yolov8_Utils.cpp:124-257）做四件事：

1. **从 32×160×160 的 mask protos 里裁出这个框对应的小块**
2. **32 维系数 × protos → 1 张 160×160 的 mask**，再 sigmoid 成概率
3. **resize 回 box 大小**，二值化（`> 0.5`）
4. **求 mask 的最小外接旋转矩形** → 填充 `rotatedBox` 和 `bigBox`

```cpp
// 第 4 步：轮廓 → minAreaRect → 加 16 像素边距 → 转回原图坐标 → 取轴对齐外接矩形
cv::RotatedRect maskOBBRect = minAreaRect(contours[0]);
maskOBBRect.size.width += 16;   // (或 height)
vertices[i] += temp_rect.topLeft();          // 转原图坐标
if (vertices[i].x > 2048) vertices[i].x = 2048;   // ← 硬编码钳制！
if (vertices[i].y > 1024) vertices[i].y = 1024;
bigBox = Rect(minX, minY, maxX-minX, maxY-minY);
```

**`box`、`rotatedBox`、`bigBox` 三者的区别**（很容易混）：

| 字段 | 来源 | 用途 |
|---|---|---|
| `box` | 模型输出 + NMS 后的轴对齐框 | 绘制绿框、Y 范围过滤、吹气孔计算 |
| `rotatedBox` | mask 轮廓的 `minAreaRect`（+16 边距） | 用 `fillConvexPoly` 抠图 |
| `bigBox` | `rotatedBox` 的轴对齐外接矩形 | 从抠图结果里切 ROI 送给分类模型 |

### 5.2 ① 从大图里抠出物体（ImageProcessing.cpp:246-283）

分四步：先在旋转矩形范围内抠出物体像素，再切轴对齐外接矩形。

```cpp

    mask(item.box).setTo(cv::Scalar(0, 255, 0), item.boxMask);
else
    continue;                       // 没有 mask 的框直接跳过

// 第二步：取 rotatedBox 的 4 个顶点
cv::Point2f P[4];
item.rotatedBox.points(P);
vector<cv::Point> pts = { {(int)P[0].x,(int)P[0].y}, {(int)P[1].x,(int)P[1].y},
                          {(int)P[2].x,(int)P[2].y}, {(int)P[3].x,(int)P[3].y} };

// 第三步：在黑色画布上把旋转矩形涂白，与原图做与运算
cv::Mat boudingGrayRect = cv::Mat::zeros(image.size(), CV_8UC3);
cv::fillConvexPoly(boudingGrayRect, pts, cv::Scalar(255,255,255), 8);
cv::bitwise_and(boudingGrayRect, image, boudingGrayRect);

// 第四步：切出 bigBox 那块 → 这就是送分类的 ROI

```

**为什么要绕这一圈？** 因为物体在传送带上是**倾斜**的。直接切轴对齐矩形会混入大量背景；先用旋转矩形抠出"只有物体"的像素，其余填黑，再切外接矩形，分类模型看到的就都是干净的黑底物体。

> ⚠ **两个潜在崩溃点**（原代码没防）：
> - `item.rotatedBox` 如果没被 `GetMask2` 填充（比如轮廓为空），`points()` 出来是 `(-1e9,-1e9)` 之类的野值
> - `image(item.bigBox)` 如果 `bigBox` 越界，OpenCV 会抛 `cv::Exception`
> 两者的共同前提是：**图片尺寸必须是 2048×1024**。尺寸不对就会踩到。

### 5.3 ② 五道过滤（ImageProcessing.cpp:286-294）

逐条解释：

| # | 条件 | 现在的值 | 含义 / 坑 |
|---|---|---|---|
| ① | `cols*rows <= 0` | — | ROI 是空的 |
| ② | `cols < 20 && rows < 20` | 20/20 | ⚠ 用的是 **`&&`**，意味着"长条物"（比如 10×500）**不会被过滤**。写 `\|\|` 才是"任一边太小就丢" |

### 5.4 ③ 跨帧去重（ImageProcessing.cpp:319-322 + 467-523）

相机连续出帧，同一个物体可能出现在相邻两帧里，不处理就会重复计数、重复吹气。

```cpp
if (State::BottleControl::RepeatJudgment && Estimate(dropRepetition, item))
    continue;
```

`Estimate` 的判据（Y 差 512 是关键）：

```cpp
if (abs(prev.box.x - cur.box.x) <= 10
    && abs(prev.box.y - 512 - cur.box.y) <= 10     // ← 上一帧的 y 减去 512
    && abs(prev.box.width - cur.box.width) <= 10)
    return true;
```

**为什么减 512？** 因为大图是两帧拼的（1024 高 = 上 512 + 下 512）。同一物体在上一帧位于下半部（y≈512+X），到本帧就跑到上半部（y≈X）。所以"上一帧 y - 512 ≈ 当前 y"就是同一个物体。

> 这条规则**只在相机连续流里成立**。本地回放是**每张图独立**的，`processCount` 却递增，导致：
> 本地第 2 张图里 y 位置恰好比第 1 张图低 512 的物体，会被误判成"重复"而跳过。
> 本地跑图时如果发现某张图少检了物体，可以先把 `RepeatJudgment` 改成 0（设置页里那个"重复判断"下拉）。

```cpp
auto range = m_clsResult.pop();
if (!range.has_value()) continue;

// ① 把"第几帧"换算成编码器位置
unsigned long long position = (range->first * 512) * State::CameraInfo::HightProportion;
// ② 加上物体在帧内的 Y
position += range->second.box.y * HightProportion;

// ③ 物体越长吹得越久
int blowExtend = 0;
if (box.height > 100) {
    blowExtend = (box.height - 100) / 50;
    blowExtend = (blowExtend <= 4) ? blowExtend : 6;
}

// ④ 吹气起始位置
int centerPost = (box.y + box.height) / 2;
unsigned long long startPost = position
    + (centerPost - box.height * ZoomRatio / 2) * HightProportion;

// ⑤ 换算成气孔编号区间
int startPort = (box.x - BlowStartX) / PoreInterval + 1;
int endPort   = (box.x + box.width - BlowStartX) / PoreInterval;

// ⑥ 逐孔下发到运动控制卡
for (int i = startPort; i < endPort; i++) {
    int car = 0, port = i;
    if (port >= 48 && MotionCarCount > 1) { car = port / 48; port = port % 48; }
    MCF_Add_Compare_Point_Net(port, startPost + BlowOffset, 1, BlowTime + blowExtend, port, car);
}
```

**核心思想**：大图不是静态画面，它的纵向是**时间轴/传送带位移轴**。
- `帧号 × 512` = 这一帧在编码器上对应的位置（每帧 512 行像素）
- `× HightProportion`（当前 4）= 像素 → 编码器单位
- 最终得到一个"提前量"，写进运动卡，等编码器走到这个值就打开对应气阀

**本地模式下这段完全不执行**，因为 `m_clsResult` 永远不会被 push。
副作用：`State::blowCounts` 仍会累加（那是在分类线程里加的，不受影响），所以界面上的"选中数量"正常，只是不吹气。

## 11. 读这份代码时会发现的几个设计问题

> 这一节不是挑刺，是"学习时值得停下来想"的点。

### 11.1 三个 worker 全是忙轮询（实测空闲占用 185% CPU）

```cpp
optional<Mat> newImg = State::frameQueue.pop();
if (!newImg.has_value() || newImg->empty()) continue;   // ← 立刻回到 while 判断，再 pop
```

`CircularQueue::pop()` 是**非阻塞**的（队列空时立刻返回 `nullopt`），而这里没有 `sleep`、没有 `wait`。
所以**没有图进来时，三个线程各自把一个核跑满**。

本机实测（无相机、无图）：`6 秒内消耗 11.13 秒 CPU` ≈ **185% 单核**，40 个线程。

框架里其实提供了阻塞版：
```cpp
std::optional<T> pop_wait(std::chrono::milliseconds timeout = 0);  // timeout=0 表示无限等待
```
改成 `pop_wait(std::chrono::milliseconds(100))` 就能把这个占用降到接近 0。

**为什么工业现场没人在意？** 因为产线一直在跑，队列几乎不空。只有在"本地调试/没接相机"时这个问题才显形。

### 11.2 `IsReadImg` 是普通 `bool`，跨线程无同步

```cpp
bool IsReadImg = false;   // ImageProcessing.h:104 ← 不是 atomic
```

UI 线程写（勾选框），worker 线程读。按 C++ 内存模型这是**数据竞争**，理论上可能读到中间状态或永不更新（实际上 x86 + 编译器没优化掉，能工作）。

`Server::readIndex` / `m_imgList` 也都没加锁，但它们只在 UI 线程里读写（`SetReadImagePath`、`DownImage`、`UpImage` 都是槽函数），所以那一对暂时安全。

**要改的话**：`std::atomic<bool> IsReadImg;` 或加 `std::mutex`。

### 11.3 坐标硬编码 2048×1024

`GetMask2`（Yolov8_Utils.cpp:230-231、247-248）：

```cpp
if (vertices[i].x > 2048) vertices[i].x = 2048;
if (vertices[i].y > 1024) vertices[i].y = 1024;
```

`ImageClsWorker` 画线（ImageProcessing.cpp:410）：

```cpp
cv::line(showImage.BigImage, Point(0,512), Point(2048,512), ...);
```

这些常量把"图像必须是 2048×1024"这个前提焊死在代码里。**换相机分辨率 = 要改这些地方**。
更好的写法是用 `image.cols` / `image.rows`。

### 11.4 本地回放的 `processCount` 语义是错的

`m_frameCounter` 每帧自增，本地回放时它也自增。于是第 5 张图的 `processCount = 4`，
吹气线程会算出 `position = 4 * 512 * 4 = 8192` 的编码器位置——**完全无意义**。

本地模式因为不吹气所以没暴露问题。但如果哪天要"本地回放 + 记录预期吹气位置"，这里是错的。

正确做法：本地模式下 `processCount` 应该是 0，或者干脆用文件名索引。

### 11.5 `showImgQueue` 会阻塞生产者

`CircularQueue<ShowImage>(20, false)` 第二个参数 `overwrite=false`。
当队列满 20 个（约 1 秒的产出），`push` 会阻塞 `ImageClsWorker`，进而反压上游。

这本来是"背压保护"，但配上 11.1 的忙轮询，会出现：**分类线程卡在 push，分割线程继续往 `m_resultYolo` 塞并覆盖**，
表现为"界面显示比实际滞后很多，且中间丢帧"。

### 11.6 `SizeLimit`、`SaveImage()`、`ImageDisplayWidget::m_zoomFactor` 都是死代码/半成品

- `State::BottleControl::SizeLimit` 读了配置，但从不判断
- `ImageProcessing::SaveImage()` 声明了没实现
- `ImageCallBackEx_New` 里的 `callbackcount` 被注释掉了
- `ConfigInfo` 里的 `SegModelPath` / `ClsModelPath` 两个 key 不存在，`Server::Init()` 里那两行是注释状态

这类"配置界面有、代码不生效"的项，改造时最容易踩。

### 11.7 相机回调里 `Mat` 包外部指针再 `push`（生命周期陷阱）

`Camera.cpp` 的 `ImageCallBackEx_New`：

```cpp
cv::Mat rawImage(512, 2048, CV_8UC3, pData);   // ← 不拥有内存，只是包了一层
cv::flip(rawImage, mirroredImage, 0);          // flip 会新建矩阵（安全）
State::frameQueue.push(mirroredImage);         // mirroredImage 持有一份拷贝
```

这里因为中间做了 `flip`，`mirroredImage` 是新分配的，安全。
但如果有人觉得"flip 没必要"直接 `push(rawImage)`，就会把**相机 SDK 的缓冲区指针**塞进队列，
回调返回后 SDK 复用缓冲区 → 下游读到的是被覆盖的脏数据（且不报错）。这是这类代码最常见的崩溃来源。

### 11.8 `Channel` 配置与 `m_clsList` 数量可能不一致

```cpp
for (int i = 0; i < State::ModelInfo::Channel; i++)
    std::string clsName = info.ClsModels[i].toStdString();   // ← 直接下标访问，没查 size
```

如果 `ModeInfo.Channel = 2` 但 `ClsModels` 只填了一个名字，`QStringList::operator[]` 越界 → 崩溃或取到空串。

```
t=8.60s    命中的框 → showImage.SmallImages
           → showImgQueue.push（包含带绿框的大图）
t=8.62s  UI 50ms 定时器取到 → 大图刷新，小图区出现 3 个 "can_0.93" 之类
t=9.00s  Timer_1s → catchCount → 写 DailyOutput / DailyOutputDetail
```

**一张图的端到端延迟 ≈ 0.6 秒**（CPU 上，主要花在分割推理）。

## 13. 想让「本地大图」跑得准，需要改什么

如果手里的图宽远超 2048（比如相机存的长条原图 12000×1024），直接喂进去必然检不出。三种改法，从易到难：

### 方案 A：先切图再跑（不改代码）

用任何工具把长条图按 2048 宽切成多段，放进一个文件夹，逐张跑。
缺点：跨段边界的物体被切成两半。

### 方案 B：改 `SetReadImagePath`，读图时自动切（改 10 行）

```cpp
// 在 DownImage 里
cv::Mat img = ReadLocalImage(path);
if (img.cols > 2048) {
    for (int x = 0; x < img.cols; x += 2048) {
        int w = std::min(2048, img.cols - x);
        cv::Mat seg = img(cv::Rect(x, 0, w, img.rows)).clone();
        if (w < 2048) cv::copyMakeBorder(seg, seg, 0,0,0, 2048-w, BORDER_CONSTANT, Scalar(0));
        State::frameQueue.push(seg);     // 每段当一帧
    }
}
```

优点：不用改流水线。缺点：结果坐标是段内坐标，跨段物体仍会被切。

### 方案 C：在 `ImageSegWorker` 里做滑动窗口 + 坐标偏移合并（改 60 行左右）

思路：
1. 按 2048 宽、步长 1536（重叠 512）切窗口
2. 每个窗口单独推理
3. 结果的 `box.x += 窗口起点`，回到整图坐标
4. 跨窗口用 NMS 合并（重叠区同一个物体会被检两次）

这是"工业上长图检测"的标准做法，也是这个项目如果要支持"跑长条大图"最该补的一块。

> 无论哪种方案，**`GetMask2` 里的 `2048` / `1024` 钳制都必须先改成 `srcImgShape.width/height`**，
> 否则窗口高 > 1024 时照样出错。

## 最后：一句话记住这条链路

> **UI 点按钮 → Server 解码成 Mat → frameQueue → 分割线程缩到 640 找框 → 分类线程按框抠图缩到 224 认品类 → 结果拆成"界面队列 / 计数队列 / 吹气队列" → UI 定时器拉取显示、1s 定时器落库。**

每一级之间都隔着一个"满了就丢老数据"的环形队列，所以这条链路是**实时优先、允许丢帧**的设计，
而不是"每张都必须处理完"的离线批处理设计。理解这一点，很多看起来奇怪的行为就说得通了。
